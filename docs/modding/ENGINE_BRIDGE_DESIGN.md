# Serialized engine bridge and Worker registry declarations

The transaction runner and opaque handles in `packages/web/src/engine-bridge/` remain an unwired engine prototype. The Worker broker now reuses its strict JSON copier for eight separately wired registry declarations in `mod-worker/gameplay.ts` and `mod-worker/registry-declarations.ts`. These declarations do not receive engine handles or live objects. `engine:access` remains refused; the fake engine exercises the transaction contract without establishing compatibility with the live game or Mandos.

The production persistence blocker is concrete: `roster.ts`'s `writeSlot` writes save bytes and roster metadata separately, then returns the conjunction of those writes. `main.ts`'s `persistSave` returns failure if either fails. A metadata failure can therefore leave changed save bytes behind even though an adapter would report rollback. Mutating a live player before that write, or staging player fields only in the serialized save, cannot satisfy the prototype's unchanged-state-and-persistence contract. Opening engine transactions requires an atomic persistence primitive, a safe-point adapter, and adversarial tests against that production adapter. A refusal-table change cannot provide those properties.

## Operation set

The host creates one handle table and one transaction runner per connection. Its authority callback supplies the measured installation identity, current authorization epoch, and current grant decision. A request contains exactly `version: 1`, `epoch`, `revision`, and a nonempty `operations` array. The caller cannot supply its identity, grants, target save, or authority callback. The host must bind that connection to one selected run and advance its epoch when the run, payload, or authorization changes. Stopping the connection calls `stop()`; an epoch change calls `advanceEpoch()` before any further work.

| Operation | Exact arguments besides `op` | Result |
| --- | --- | --- |
| `actor.read` | `handle`, `field` equal to `name`, `health`, or `maxHealth` | A string or number copied from the transaction snapshot |
| `actor.setHealth` | `handle`, integer `health` from 0 through 1,000,000 | `null`; health cannot exceed the actor's maximum |
| `actor.rename` | `handle`, nonempty `name` of at most 80 UTF-16 code units without ASCII control characters | `null` |

The host issues handles for selected actors. Each handle contains its epoch and 256 cryptographically random bits and resolves only within its table's installation and epoch. Including the epoch prevents reissuing an old handle even if random bytes repeat. The table retains at most 256 live targets. Stop and epoch advance clear every entry; stop is terminal, and epochs cannot rewind. Tests use `WeakRef` in a process with explicit garbage collection to check that revoked targets become collectible while their tables remain alive. Workers receive only the opaque string and primitive operation results.

## Transaction boundary

The runner validates and copies the entire request, checks every operation schema, and resolves every handle before reading the engine. The engine supplies a snapshot of at most 128 actors with unique identifiers and a revision. The runner validates and copies that snapshot before changing anything, so even an adapter that returns live state cannot expose it through the runner. Reads observe earlier changes within the batch. A later invalid operation discards all staged changes and results.

Before commit, the runner validates the resulting state and complete reply, then checks the host's authority again. Any removed grant, changed installation, changed epoch, stopped table, or stale revision refuses the batch. A mutating batch advances the revision once. The adapter's synchronous `commit(expectedRevision, next)` must compare the revision and atomically publish state and persistence, or leave both unchanged on refusal or failure. The runner never calls a separate save operation, and read-only requests never commit. The fake adapter implements this contract and tests rollback, persistence failure, and a revision conflict.

This adapter contract is a prerequisite for a production integration. A production adapter cannot mutate live state and then attempt a fallible save without rollback. It must also bind the snapshot revision to the current save and turn, run at a host safe point, apply permanent consequence marking before exposing sensitive results, and preserve recovery state. The prototype supplies none of those game-specific integrations. Its synchronous critical section has no callbacks into mod code, asynchronous work, or yielding hooks. Trusted adapter methods must not reenter lifecycle changes during commit.

## Rejection and resource limits

The data copier accepts only finite JSON primitives, dense arrays, and plain records with enumerable data properties. It rejects accessors without invoking them, symbol keys or values, functions, classes, class instances, non-plain prototypes, hidden properties, cyclic values, and the keys `__proto__`, `constructor`, and `prototype`. Schema checks reject these spellings as field names or operation names, dotted paths, array paths, extra arguments, unknown operations, generic invocation, and constructor recovery. The only field lookup uses the three enumerated snapshot fields. There is no route to consent, private storage, credentials, DOM objects, or desktop bridges.

The same copier rejects `SharedArrayBuffer`, `Atomics`, `Atomics.wait`, typed arrays, `DataView`, `ArrayBuffer`, ports, streams, and other transferable or host objects because they are outside this data grammar. Neither direction supplies a transfer list or a shared-memory channel. Tests submit these values directly to the runner, including a shared-memory typed view, without depending on a Worker-side JSON serializer to remove them first. Browser-specific transferable types are excluded by the same prototype check; they are not instantiated by these Node tests. Proxies with executable traps are outside the serialized transport assumption, since structured clone cannot deliver a Proxy to the host.

Both input and copied engine snapshots are limited to 64 KiB of serialized UTF-8 data, depth 12, and 4,096 visited values. A batch contains at most 32 operations. The complete reply has the same byte, depth, and node limits; the fixed operation schemas further bound each returned primitive. Each connection admits at most 32 calls per fixed 1,000-millisecond window, including malformed requests. The host uses a monotonic clock, and the runner rejects a reversed or invalid clock. One transaction can run at a time, including during trusted adapter reentry. A host must retain the same runner for the connection lifetime so rejected calls and epoch changes cannot reset its rate counter.

These bounds limit work within the prototype. Registry requests now use the copier over the actual Worker broker and add connection-wide declaration count, retained-byte, concurrent-work, and write-frequency limits. They do not provide browser CPU or memory isolation, validate a future engine adapter, or contain code already executing in the game page.

## Deliberately missing

Arbitrary callbacks, live synchronous hooks, object traversal, generic invocation, module loading, constructors, evaluation, networking, storage, save selection, and transferables remain absent from the engine bridge. The separately wired registry declarations open `effect`, `room`, `profile`, `blow`, `glyph`, `randart`, `vocab`, and `menu` through the exact data schemas in `API2.md`. `registry:*` remains closed because `monster`, `projection`, `effect-info`, and `rune` still lack Worker mechanisms. Additional gameplay operations require separate schemas, invariants, bounded implementations, and adversarial tests. Arbitrary engine callbacks require an isolated gameplay runtime; shared memory and `Atomics.wait` cannot substitute for that boundary.
