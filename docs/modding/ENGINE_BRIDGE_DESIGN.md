# Serialized engine bridge and Worker registry declarations

The transaction runner and opaque handles in `packages/web/src/engine-bridge/` form an engine prototype that is still unwired. One part of it reaches the game: the Worker broker reuses its strict JSON copier for eight separately wired registry declarations in `mod-worker/gameplay.ts` and `mod-worker/registry-declarations.ts`. Those declarations get no engine handles and no live objects. A mod that asks for `engine:access` is still refused. The tests run the transaction contract against a fake engine, so passing them says nothing about compatibility with the live game or Mandos.

Production saves keep the bridge closed. In `roster.ts`, `writeSlot` writes the save bytes and the roster metadata as two separate writes and returns the conjunction of the two results, and `main.ts`'s `persistSave` returns failure if either write fails. If the metadata write fails, the changed save bytes stay behind even though an adapter would report a rollback. Mutating the live player before that write fails the prototype's contract that state and persistence stay unchanged together, and so does staging player fields only in the serialized save. Engine transactions can open only with an atomic persistence primitive, a safe-point adapter, and adversarial tests against that production adapter. Editing the refusal table provides none of these.

## Operation set

Each connection gets one handle table and one transaction runner from the host. The host's authority callback supplies the measured installation identity, the current authorization epoch, and the current grant decision. A request holds exactly `version: 1`, `epoch`, `revision`, and a nonempty `operations` array, and nothing else: the caller cannot pass in its identity, its grants, a target save, or an authority callback. The host binds the connection to one selected run and must advance the epoch whenever the run, the payload, or the authorization changes. Stopping the connection calls `stop()`. An epoch change calls `advanceEpoch()` before any further work runs.

| Operation | Exact arguments besides `op` | Result |
| --- | --- | --- |
| `actor.read` | `handle`, `field` equal to `name`, `health`, or `maxHealth` | The string or number from the transaction snapshot, as a copy |
| `actor.setHealth` | `handle`, integer `health` from 0 through 1,000,000 | `null`; health is capped at the actor's maximum |
| `actor.rename` | `handle`, nonempty `name` of at most 80 UTF-16 code units without ASCII control characters | `null` |

Handles exist only for actors the host selects. A handle carries its epoch plus 256 cryptographically random bits, and it resolves only inside its own table's installation and epoch. Because the epoch is part of the handle, an old handle cannot come back into use even if the random bytes repeat. A table holds at most 256 live targets. Both stop and epoch advance clear every entry. Stop is terminal, and an epoch never moves backward. The tests run in a process with explicit garbage collection and use `WeakRef` to check that revoked targets become collectible while their tables are still alive. A Worker only ever sees the opaque handle string and primitive operation results.

## Transaction boundary

Nothing touches the engine until the whole request has been validated and copied, every operation has passed its schema, and every handle has resolved. The engine then supplies a snapshot of at most 128 actors with unique identifiers, plus a revision. The runner validates and copies that snapshot before it changes anything, so an adapter that hands back live state still cannot leak it through the runner. Within a batch, a read sees the changes made by earlier operations. If a later operation is invalid, every staged change and result is discarded.

Before committing, the runner validates the resulting state and the complete reply, then asks the host for authority a second time. The batch is refused if a grant was removed, the installation changed, the epoch changed, the table was stopped, or the revision is stale. A batch that mutates anything advances the revision by exactly one. The adapter's synchronous `commit(expectedRevision, next)` must compare the revision and publish state and persistence atomically, or leave both untouched when it refuses or fails. The runner never calls a separate save operation, and a read-only request never reaches commit. The fake adapter implements this contract, and its tests cover rollback, persistence failure, and a revision conflict.

Any production integration needs an adapter that meets this contract. Mutating live state and then trying a save that can fail, with no rollback, does not qualify. A production adapter also has to bind the snapshot revision to the current save and turn, run at a host safe point, apply permanent consequence marking before any sensitive result is exposed, and preserve recovery state. The prototype implements none of these game-specific pieces. Its synchronous critical section makes no callbacks into mod code, does no asynchronous work, and has no yielding hooks. Trusted adapter methods must not reenter lifecycle changes during commit.

## Rejection and resource limits

The data copier accepts finite JSON primitives, dense arrays, and plain records whose properties are enumerable data properties. It rejects accessors without calling them. It also rejects symbol keys and symbol values, functions, classes, class instances, non-plain prototypes, hidden properties, cyclic values, and the keys `__proto__`, `constructor`, and `prototype`. The schema checks refuse those same spellings as field names and operation names, along with dotted paths, array paths, extra arguments, unknown operations, generic invocation, and constructor recovery. Field lookup happens in one place and only for the three enumerated snapshot fields. No operation leads to consent, private storage, credentials, DOM objects, or desktop bridges.

`SharedArrayBuffer`, `Atomics`, `Atomics.wait`, typed arrays, `DataView`, `ArrayBuffer`, ports, streams, and other transferable or host objects fall outside this data grammar, and the copier rejects them. Neither direction passes a transfer list or opens a shared-memory channel. The tests hand these values straight to the runner, including a typed view over shared memory, so the rejection does not depend on a Worker-side JSON serializer stripping them first. Browser-specific transferable types fail the same prototype check, though these Node tests do not create them. Proxies with executable traps are outside the serialized transport assumption, since structured clone cannot deliver a Proxy to the host.

Input and copied engine snapshots are each capped at 64 KiB of serialized UTF-8 data, depth 12, and 4,096 visited values. A batch holds at most 32 operations. The complete reply has the same byte, depth, and node caps, and the fixed operation schemas also bound each primitive it returns. A connection gets at most 32 calls per fixed 1,000-millisecond window, and malformed requests count. The host supplies a monotonic clock. A clock that runs backward or returns an invalid value makes the runner reject the call. Only one transaction runs at a time, and that holds during trusted adapter reentry too. The host must keep the same runner for the whole life of the connection, so that neither rejected calls nor epoch changes can reset the rate counter.

These caps bound the work done inside the prototype. Registry requests run the copier over the actual Worker broker and add connection-wide limits on declaration count, retained bytes, concurrent work, and write frequency. None of these limits isolates browser CPU or memory, validates a future engine adapter, or contains code that is already running in the game page.

## Deliberately missing

The engine bridge has no arbitrary callbacks, live synchronous hooks, object traversal, generic invocation, module loading, constructors, evaluation, networking, storage, save selection, or transferables. The separately wired registry declarations open `effect`, `room`, `profile`, `blow`, `glyph`, `randart`, `vocab`, and `menu`, each through the exact data schema in `API2.md`. `registry:*` stays closed because `monster`, `projection`, `effect-info`, and `rune` have no Worker mechanism yet. Each new gameplay operation needs its own schema, invariants, bounded implementation, and adversarial tests. Arbitrary engine callbacks need an isolated gameplay runtime, and shared memory with `Atomics.wait` cannot stand in for that boundary.
