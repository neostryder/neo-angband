# Worker mod isolation

A Worker mod runs in a Worker that talks to the game only through bounded JSON messages relayed by a sandboxed frame. To declare one, set `"runtime": "worker"`, give an `api` range over API 2, and name an `entry`. The mod has no direct network or game-storage access. It can build data: code at runtime and import it dynamically, and that code runs under the same sandbox restrictions. A Worker is the isolated way to run a mod. A mod that does not need isolation can run in process with the same API and none of these limits.

API 1 plugins are not covered. They run in the game's page with the game's own access and are trusted code (`PLUGINS.md`).

A Worker can declare bounded effect programs, room primitive choices, copied dungeon profiles, fixed-damage blows, glyph mappings, randart combat stats, private vocabulary terms, and gameplay menu row rules. Before registration, the host validates the JSON and saves the permanent scoring and determinism consequences. Each synchronous callback runs as host code that checks its connection, epoch, binding, and live grant. If the Worker stops or stalls, the game falls back to host behavior and no game tick waits on it. `API2.md` gives the exact schemas and quotas under "Worker registry declarations". `registry:*` stays closed because four of the domains it covers have no Worker mechanism. `engine:access` stays closed because the current save writer cannot do an atomic engine commit and rollback, and Workers get no live engine objects.

## How a Worker mod starts

1. The game reads every module reachable from the mod's entry through literal imports (`packages/web/src/mod-worker/staging.ts`). A module counts as the mod's own if it is a file under the entry's folder on the game's origin, or a blob: URL the game created for a mod folder picked in a browser. The only package allowed is `@rpgm-tools/neo-angband-mod-sdk/authoring`, which stages a fixed pure library, and only when the mod has `mod:authoring`. Before any code runs, the game refuses any other bare package name, another origin, a data: URL, a path out of the folder, a query string or fragment, and any import cycle, and the error names the file at fault. A graph, the authoring library included, can hold at most 256 files and 16,777,216 characters of source (16 Mi).
2. The game adds a hidden `<iframe sandbox="allow-scripts">` whose document comes from `srcdoc` (`packages/web/src/mod-worker/isolation.ts`). The sandbox omits `allow-same-origin`, so the frame has an opaque origin. Its document sets a Content Security Policy before its single script runs.
3. The game sends a hello message that transfers a control MessagePort and carries a fresh nonce, the same one embedded in the frame. The frame checks the parent and the nonce, accepts only one hello, and echoes the nonce back on the port. Only after that acknowledgment does the game send the module text and a second port, over the control port. No module source goes to the frame window. A wrong nonce, a wrong source, or a replayed hello cannot start another Worker.
4. The frame turns each module into a `data:` URL, putting each import's own `data:` URL where the import stood, then starts a classic Worker from a `data:` URL. The Worker inherits the frame's opaque origin and its policy.
5. The Worker deletes its network, storage, shared-memory, canvas, blob, and nested-worker globals. If a forbidden name is still reachable, it aborts before importing the entry, with a failure message of at most 1,024 characters. It then freezes the MessagePort and MessageEvent prototypes and constructors, installs the API 2 bootstrap on a private transport, and imports the entry. The bootstrap checks that the default export is an API 2 definition and reports its declarations to the broker.

After boot, the frame keeps both page-facing ports, and the Worker never receives one. The Worker sends JSON text to the frame. The frame rejects raw objects, transferred ports, invalid JSON, non-finite numbers, nesting deeper than 64 levels, and messages over 64 KiB, and posts only parsed data to the page. Through this relay the mod talks to the game's broker (`host.ts`). The broker serves each call with the same API 2 host an in-process mod gets, under the permissions the player granted, and [API2.md](API2.md) lists its limits under "In a Worker". The second port carries only Worker errors to the game and the order to stop. Stopping the mod terminates the Worker and removes the frame.

A mod that fails any step fails to start, with a problem line on the Mods screen. So does a Worker that has not answered as ready within 3 seconds. Nothing falls back to an unisolated Worker.

The broker's operations include `view.*`, `store.*`, `backupFolder.*`, and granted truth snapshots. `truth.level()` and `truth.storeKnowledge()` need `state:map-actual.read`. `truth.monsters()` and `truth.race(index)` accept either that grant or `state:monsters-actual.read`, and their snapshots include unseen monsters and true race abilities. The same rule applies to every author. Before building a snapshot, the broker checks the connection identity, epoch, arguments, and current grant, then waits for confirmation that the character's permanent unscorable mark and provenance are saved. If that save is missing or fails, or the session has no character, the call returns no hidden data. If the grant is revoked or the epoch changes before delivery, the reply is dropped. The existing limits of 4 MiB per reply and 200 calls per second apply, and a reply over the size limit still leaves the mark in place. The named management operations in [API2.md](API2.md) use their own host confirmations. Workers have no engine access and no raw presentation.

The content broker accepts bounded repository references or archives of up to 12 KiB, and keeps one measured plan per Worker API for 60 seconds. Install and session apply requests consume the plan before the host dialog opens, and refuse a changed digest afterward. They accept records and tweaks only, with no code and no capability grants. Installed content arrives switched off, and an install refuses an id that already exists. Session archives cannot shadow installed ids or gain authority from session records the page wrote. Repository fetches go to fixed GitHub hosts, send no credentials, and have ceilings on requests, bytes, and files. Browser fetches refuse redirects. Desktop metadata lookups use a separate native repository authority plus the relay's destination, redirect-hop, and DNS guards, and they return no file text. Quit and exit-to-title ask the player before the game's save-first path runs. Wizard requests ask before giving up save writes permanently, verify detachment, and mark the live character unscorable before exposing the serialized wizard proxy. All of these calls go through the host's management serialization and share its limit of 32 requests per mod per minute.

## The three layers

Worker text replacements and grid regions carry only bounded line records, fixed style tokens, and grid coordinates. The host draws them with `textContent`, clips them to validated geometry, caps them at eight outputs, and hides them whenever a host dialog or another modal screen owns the display. The Worker gets no DOM, canvas, callback, or transferable handle for these regions.

The simple Worker grants add bounded data paths for interface options, edits to the current keyset, and named visual filters. Before dispatch, the broker checks both its connection's grants and the host's current grants, and the host rechecks a pending key capture before returning it. A host dialog cancels capture and suspends mod panels and filters. A permission dialog also stops delivery of keys and decisions to a Worker controller. Through these paths a Worker never supplies CSS for a filter and never receives a live key event. [API2.md](API2.md) lists the methods and bounds.

| Layer | What it stops | Where |
|---|---|---|
| Opaque origin | IndexedDB, Cache Storage, and the origin-private file system either refuse an opaque origin or give it an empty store of its own. Nothing in the origin is same-origin with the game, so the game's URLs and blob: URLs are out of reach. | the frame's `sandbox` attribute; the `data:` Worker |
| Content Security Policy | `connect-src 'none'` refuses fetch, XHR, WebSocket, EventSource, and WebTransport before any request goes out. `script-src` admits only the frame's nonce and `data:`, so no remote script or module loads and `eval` is refused. `worker-src` and `child-src` admit `data:` for the one Worker. Every other directive, `default-src` included, is `'none'`. | `modFrameCsp` |
| Global lockdown | Before the mod loads, the lockdown deletes network, storage, and nested-worker globals, BroadcastChannel, WebRTC constructors including prefixed forms, SharedArrayBuffer, Atomics, OffscreenCanvas, Blob, URL.createObjectURL, storage/cache constructors, and navigator.sendBeacon, serviceWorker, storage, and locks, along their prototype chains. A writable name that cannot be deleted is set to `undefined`, and any leftover that is still reachable aborts boot. | `lockDownModWorkerScope` |

The opaque origin and the CSP block page, storage, and network access even when the probe turns off global deletion. Production boot also requires global deletion to succeed. Workers can normally share memory through SharedArrayBuffer, so this host deletes that global and Atomics, and the frame relay refuses shared memory and transferable handles. The isolation does not rely on the desktop page's cross-origin isolation headers staying out of srcdoc. Dynamic import is language syntax, so it cannot be deleted from the scope.

## Why data: URLs and a classic Worker

These were measured in an opaque-origin frame with Playwright:

| | Chromium | Firefox | WebKit |
|---|---|---|---|
| Module Worker from a blob: URL | refused | starts | refused |
| Classic Worker from a blob: URL | starts | starts | refused |
| Importing a blob: module made by another context | only from a blob: Worker | only from a blob: Worker | refused |
| Classic Worker from a data: URL, importing data: modules | starts | starts | starts |

The frame uses the last row because it is the only combination the existing harness supports in all three engines. Removing data: from script-src would block the staged-module imports. The current loader has no measured blob/module URL alternative for that matrix, and dynamic imports are not yet restricted to measured sources. As a result, text the broker provides can become runtime code inside the sandbox. A classic Worker still has `import()`, and that is how it loads the mod's modules. In all three engines the `data:` Worker inherits the frame's policy.

## Browser and desktop

The browser game and the desktop app use the same frame. The desktop app serves the game from its own `neo-angband://game` scheme, every response on that scheme carries the headers that make the page cross-origin isolated, and the window runs with `contextIsolation`, `sandbox`, and no Node integration. A `srcdoc` frame has no response of its own, so those headers do not affect it, and the frame and its Worker behave as they do in Chromium. The frame relay rejects non-JSON Worker traffic before it reaches the page. The desktop setup provides no separate process and no CPU or memory quota.

## Game-page policy and parent-page trust

The desktop response headers and the Vite preview server send `Content-Security-Policy-Report-Only`. The web bundle also emits `_headers` for static hosts that read that file. Other hosts, GitHub Pages included, need the response header configured outside the bundle. A meta element cannot deliver a report-only CSP. The report-only policy defaults to no loads, permits same-origin and blob scripts without eval or inline scripts, and permits HTTPS connections for existing network operations. Browsers only report violations of it and block nothing. The game has not been verified under an enforced page policy, and page restrictions inherited by the frame would currently conflict with its inline bootstrap and data: module imports.

The nonce handshake defeats blind races and keeps module source out of window messages. It gives no protection against arbitrary code already running in the parent page. Such code can read srcdoc, hook MessageChannel or postMessage, and act with page authority, and no handshake inside a page can hold a secret from that page. Code running in the page is therefore trusted, and a full guarantee against a hostile parent script is not yet in place.

## What the tests prove

- `packages/web/src/mod-worker/staging.test.ts` covers the staging rules: which files are read, in what order, and every refusal.
- `packages/web/src/mod-worker/host.test.ts` connects the actual bootstrap to the broker in one thread, running on an actual game. Two games that differ only in an unseen monster look the same through the Worker and the same as through the in-process host. The file also covers an answer that times out and the late reply that follows it, the wildcard grant, policy tables answering within a turn, a credential that never reaches the Worker, and stopping a stalled Worker.
- `packages/web/src/mod-worker/isolation.test.ts` runs the actual frame script and Worker source against stand-ins. It covers the policy text, lockdown leftovers aborting before the entry runs, the standalone shipped source, broker round trips, teardown, boot attempts with a wrong source or wrong nonce, replays, the JSON-only relay limits, the link limit, and frame load failures.
- `tests/e2e/mod-worker-isolation.spec.ts` runs a probe mod in Chromium, Firefox, and WebKit, with the lockdown on and off. The probe tries the game's IndexedDB, Cache Storage, and private file system, network APIs, remote imports, eval, nested Workers, BroadcastChannel, SharedArrayBuffer, Atomics, OffscreenCanvas, Blob, object URLs, sendBeacon, service workers, storage estimates, locks, and WebRTC constructors including prefixed forms. It also tries replacing the MessagePort and MessageEvent prototypes, and sends raw typed arrays and a transferred port outside the API proxy. A separate, unmocked Worker with an immutable forbidden global has to abort before the entry runs. A runtime data: import succeeds, but code imported that way cannot fetch the game or reach its page. The test counts every request the page makes. In every engine the probe's origin is `null`, every network attempt fails, no store holds the game's data, `eval` is refused, and the page makes no request. A control run of the same probe as a plain Worker on the game's origin opens the game's IndexedDB and Cache Storage, runs `eval`, and imports the remote module. That run shows each check can detect an open door.
- `tests/e2e/mod-worker-isolation.electron.spec.ts` runs the same probe in the repository's Electron, with the desktop shell's scheme, privileges, headers, and window settings, and with the main process counting every request. It first checks that the page is `neo-angband://game`, cross-origin isolated, and a secure context. The isolated runs pass the same checks as in the browsers, every store refuses the probe even with the lockdown off, and no request reaches the main process. The control run reads the game's IndexedDB and fetches a game file, and the main process sees those requests. The test uses a small stand-in for the shell's main process, because the packaged-app fixture needs a release build.

The page script in both specs is bundled by Vite with minification, so the frame and Worker source that ship as `Function.prototype.toString()` text are tested in the shape a release build gives them.

Run them with `pnpm exec playwright test tests/e2e/mod-worker-isolation.spec.ts` and `pnpm exec playwright test --project=electron tests/e2e/mod-worker-isolation.electron.spec.ts`.

## What it does not stop

- **What the broker allows.** A mod can send out whatever its granted capabilities let it send, and can misuse an action the player approved. The broker's checks are its own subject.
- **Resource use.** The Worker shares the renderer's CPU and memory. An endless loop or allocation flood slows or crashes the tab. The broker's rate and size limits, and its heartbeat, which stops a Worker that goes 5 seconds without answering, soften this; they are not a quota.
- **Side channels.** Timing and covert channels are not addressed.
- **BroadcastChannel without the lockdown.** It opens, scoped to the frame's opaque origin, which each sandboxed frame gets afresh. Two mods running at once were not tested against each other; the lockdown removes the API in any case.
- **Empty stores of its own.** WebKit gives the Worker an empty Cache Storage of its own. It holds nothing of the game's and is gone with the frame.
- **Engine bugs.** This is not a VM or a process boundary. It depends on Chromium, Gecko and WebKit enforcing the sandbox and the policy, and on the desktop app's Electron being kept current.

## Worker management operations

After player consent, the broker permits these operations for every author: `manage.profiles.list/create/switchTo/rename` under `profiles:manage`, `manage.session.save` under `session:control`, `manage.options.get/set` under `options:manage`, and `manage.saves.list/load/rename/delete` under `saves:manage`. A Worker can manage only the profiles it created, profile creation takes no copy source, and creating a character requires destination-local stored consent. The character picker returns only entries the player selected, identified by opaque ids the host issues, never raw slot ids. The host draws a confirmation for every mutation, and deleting the active character is refused even after confirmation. Before a cheat option is applied, the game persists an unscorable mark. Birth and score options stay locked.

`profiles:manage` also permits an identity-only `manage.mods.snapshot`, changes to the caller's own disable, setting, section, and conflict choices, and withdrawal of third-party consent. Each of these mutations requires a host confirmation and writes no capability consent. The broker validates the exact shape and size of every argument, allows one management operation in flight across the whole game, and allows 32 management requests per mod per minute. Before committing, it checks caller identity, epoch, current grant, measured payload binding, profile/session scope, and plan stability. Selecting a new character invalidates earlier opaque ids. Resuming a Worker controller keeps its separate consent dialog.

Through this surface, Workers cannot resolve confirmations, write permission decisions, enable or install code, load session packs, or call engine or live presentation objects. The Mods screen can be replaced through the separate data-only presenter path. Quit, exit-to-title, and wizard stay refused until detachment from saves is proven.

## Worker presenters

`ui:menu.replace`, `ui:screen.replace`, `ui:birth.replace`, `screens:manage`, and `display:replace` work through JSON descriptions that the host draws, never through live presenters. Callback functions stay inside the Worker. The host asks the Worker for descriptions or delivers opaque row selections tagged with host-issued presentation ids. The host validates original menu choices. A screen selection can dismiss or refresh its description, up to 64 refreshes. Live screen action handlers stay closed because their asynchronous mutations have no Worker grant check at commit, so requests for those actions fall back to the game's screen. The host never interprets mod strings as markup, CSS, resource URLs, or code. No DOM node, canvas, OffscreenCanvas, transferable, or SharedArrayBuffer crosses the presenter port. [API2.md](API2.md) lists the runtime methods and schemas.

A description can hold 64 lines, 64 rows, and 32768 bytes, and all registrations share a limit of eight per second. A map frame can hold 512 glyphs and 60000 bytes, uses fixed color tokens, and is clipped to the game's map region. Map frames run at most ten times per second with one request outstanding, and a 250 ms deadline declines slow answers. Map output holds a 250 ms lease over the game's own display, so the host map shows again on expiry, failure, suspension, a geometry change, or a stale answer. Before drawing or accepting a selection, the host checks connection identity, epoch, measured binding, current grant, and game-state identity.

Interactive output occupies the map rectangle, below native modal dialogs, and keeps the host Close and fallback controls. The Mods replacement always shows Permissions and game controls above mod panels. This control opens the game's own Mods screen with panels suspended and all navigation drawn by Core, so no other presenter can intercept access to permissions. Core permission and controller questions cancel and hide presenters, even when a gameplay modal was already open. Map output also suspends for ordinary gameplay dialogs, and screen presenters yield to host prompts. Raw keys never reach these callbacks, and Escape dismisses them in the host. Late selections and stale buttons cannot invoke actions. Birth uses at most 64 host-owned steps, fresh opaque step and choice ids, the game's legal race, class, and stat operations, and bounded name and background proposals. Birth and score options stay locked. The Worker can request review but cannot accept. A separate host modal shows the actual character and every birth option, suspends mod output, and rechecks authority and that the draft is unchanged before acceptance. The `ui:*.replace` wildcard now covers all six families: messages, sidebar, status, menu, screen, and birth. It grants no map, region, or panel authority, and an explicit refusal of a family takes precedence. These limits add no CPU, memory, process, or browser-engine boundary.

Worker `backup:folder` uses the desktop authority table. The player picks the folder through native folder selection that names the mod, and a native confirmation naming the mod, file, and folder appears before each write. Paths and native authority handles never reach the Worker. After confirmation and before consuming a single-use, 30-second plan, the host rechecks the Worker epoch, grant, binding, and game-state identity. The desktop binds each plan to native authority and the selected per-installation allocation. Custom writes accept plain `.neochar` filenames and up to 32768 UTF-8 bytes, with one operation pending and 16 requests per minute. Desktop plan requests and commits share a limit of 32 per minute. Listings contain file names with empty character metadata. Save notifications share the reply byte budget and carry only an opaque file id, name, and size. The host keeps one latest file of at most 8 MiB for each Worker. `writeSaved(id)` writes that file's exact bytes under its host filename without releasing the contents to the Worker or accepting an upload from it. If the file or the authority changes, the id becomes invalid, including while the native confirmation is waiting. Existing desktop quotas and link checks apply. Browser-only Workers cannot use this mechanism, and larger custom uploads or host files beyond 8 MiB require a bounded mechanism.

## Worker spawning and publication

`debug:spawn` opens only `debug.spawnObject` and `debug.spawnMonster`. Each call names a known content id, name, or index and requests 1 to 16 creations. Every request opens a host-drawn native dialog that names the mod's display name and id, the content, and the count. The host persists the permanent debug score mark and the `spawn` consequence before any creation becomes observable. A decline, writer failure, revocation, changed binding, or stale epoch stops the spawn. A mod gets four spawn requests per minute, and only one spawn dialog runs at a time. Wizard controls stay refused.

`shared:read` reads only what other mods explicitly publish. `shared:publish` publishes or withdraws values under the caller's host-owned id, never under an identity the Worker supplies. Readers cannot inspect a mod's private storage. Values cross as JSON copies in both directions, with limits of 16 KiB per value, 32 entries per publisher, and 16 combined shared calls per mod per second. The first publication in each Worker session persists `shared-write` once, with no dialog and no score penalty, and it needs a character with a working save writer. All other readers can see a publication, and publishing transfers no authority. These operations also check the current grant, measured binding, identity, and epoch, and they count against the existing transport quotas. No live callback or host object crosses this domain.

## Refused permissions

A broker request that needs an ungranted permission resolves to `{ ok: false, reason: "not-granted", capability }`. This applies during startup too, so awaiting a refused preference read does not prevent the Worker from becoming ready. Methods that normally return no value also return this result on refusal. Invalid payloads and operational failures still reject. Host-rendered Worker panels and in-process API 2 panels stay hidden and inert while a Core confirmation is open, including panels mounted or patched during that confirmation.

## What it asks of a Worker mod

- Import only the mod's own files, by relative path. A bare package name has to be bundled in.
- No import cycles.
- No `import.meta.url` and no computed dynamic imports of the mod's files: a module is a `data:` URL, so neither resolves to a file. Read files with `content.asset` instead.
- Each module carries the `data:` URLs of its imports inside it, so a deep or diamond-shaped graph grows faster than its source. Linking stops at 64 MiB with a message; bundling a mod into one file avoids the question.
